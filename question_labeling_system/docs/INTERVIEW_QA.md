# 智能题目标注补录系统：面试问答

## 1. 请介绍项目解决了什么问题

**回答：**

公司原来由业务人员逐题选择语文、数学、英语填空题属性标签，例如答案不唯一、多空题、单位要求、时态考点。系统利用 100 万以上历史人工数据训练多标签模型，再结合规则、Hybrid RAG 和 LangChain LLM 生成默认标签。Vue 补录页展示模型建议、分数和相似题，人工确认后提交。最终标签继续进入评测和训练闭环。

核心目标不是完全替代人工，而是降低每题点击和判断成本，同时保持业务可控与可审计。

## 2. 为什么不用一个大模型直接打标签

**回答：**

纯 LLM 有四个问题：成本、延迟、概率性和对公司历史规范不了解。项目采用分层信号：规则处理明显题型，轻量监督模型吸收百万历史分布，RAG 提供最新相似人工案例，LLM 只负责复杂语义综合与解释。即使 RAG 或 LLM 暂时故障，系统仍可给出部分建议并允许人工完成任务。

## 3. 这是多分类还是多标签问题

**回答：**

是多标签。数学题可能同时是“需要计算”“必须带单位”“多空题”。多分类只能选一个类别；多标签对每个标签独立判断。评测需要 micro/macro F1、exact match 和逐标签指标，而不是普通 accuracy。

## 4. 100 万数据为什么选 HashingVectorizer + SGDClassifier

**回答：**

这是低成本、可解释、可流式训练的生产基线。HashingVectorizer 不保存巨大词表，字符 n-gram 同时适配中文、英文拼写、数学符号和单位；SGDClassifier 支持 `partial_fit`，内存由 batch 控制。它不是最终唯一方案，后续会与 Transformer 分类器和 SFT 模型在同一固定评测集上比较。

## 5. 如何防止训练集泄漏

**回答：**

当前代码按 `external_id` 稳定哈希切分，保证同一道题不会跨集合。真实生产还要按母题 ID、来源文档或规范化题干哈希分组，把改写题整体放进同一分区，并增加时间外测试集。否则近重复题会让指标虚高。

## 6. 为什么要加 RAG

**回答：**

监督模型将历史知识固化在参数中，标签规范或题型变化后容易滞后。RAG 在预测时找回同学科、人工确认过的相似题，补充最新判定先例和可追溯证据。人工页面能看到证据，不需要盲信模型解释。

## 7. Dense 和 Sparse 分别解决什么

**回答：**

Sparse 使用 MySQL ngram FULLTEXT，擅长诗句、固定术语、数字、单位和精确词面；Dense 使用 Embedding + Qdrant，擅长同义表达和改写题。两者互补，单一路由容易漏掉另一类相关性。

## 8. 为什么使用 RRF，不直接加分

**回答：**

MySQL FULLTEXT 分数和向量余弦分数不是同一概率空间，直接加权可能让某一路因数值尺度占优。RRF 使用各路排名：

$$
score(d)=\sum_r\frac{w_r}{k+rank_r(d)}
$$

它不要求原始分数可比，并自然提升两路都靠前的候选。

## 9. LangChain 在项目中做什么

**回答：**

LangChain 负责模型适配、`ChatPromptTemplate`、LCEL 组合和 Pydantic 结构化输出。`LangChainLabelReasoner` 将 Prompt 与 `with_structured_output(ReasonerOutput)` 组合，保证模型只能返回标签、置信度、理由和 evidence ID 的结构。

结构正确不等于业务正确，所以未知标签仍由代码过滤，最终由人工提交。

## 10. LangGraph 在项目中做什么

**回答：**

LangGraph 将在线预测显式拆成 normalize、rules、retrieve、historical_model、reason、ensemble 六个节点。每一步输入输出清楚，RAG 和 LLM 可独立降级，最终融合策略可测试和版本化。

固定线性流程理论上也能用 LCEL，但这里需要状态、节点级错误边界、后续条件路由和可观测扩展，因此使用 LangGraph 更清楚。

## 11. 这算 Agent 吗

**回答：**

当前主链更接近受控 Agentic Workflow，不是让模型自由决定所有步骤的通用 Agent。检索、监督模型、融合和人工终审的拓扑由代码确定，LLM 只在 `reason` 节点做语义判断。这种设计更符合高风险数据补录：需要智能判断的地方用模型，需要确定性的地方用代码。

## 12. 为什么模型不能直接提交最终标签

**回答：**

标签是业务事实，会影响题库、判分和下游分析。模型输出具有概率性，RAG 也可能召回旧规范或错误样本。系统只把模型标签设为默认选择，人工提交才进入 `human_annotations`，并保存操作员、预测版本和差异。

## 13. 如何保证多人补录不互相覆盖

**回答：**

先用 `SELECT FOR UPDATE SKIP LOCKED` 和租约降低同题并发；提交时再使用乐观锁 `expected_version`。如果题目版本已变化，API 返回 409，页面要求刷新。租约是协作体验，版本校验是最终一致性保护。

## 14. 为什么需要幂等键

**回答：**

用户点击提交后可能网络超时，前端或网关会重试。如果没有幂等键，同一次操作会产生两条人工记录。`human_annotations.idempotency_key` 有唯一约束，相同键重试返回原记录，不重复改变任务状态。

## 15. 为什么不用 FastAPI BackgroundTasks 做批量预测

**回答：**

BackgroundTasks 与 Web 进程同生命周期，重启后任务丢失，也不适合独立扩缩容和长时间模型调用。项目用 MySQL `prediction_jobs` 做可靠队列：题目和任务同事务创建，Worker 用租约领取，失败按上限退避，崩溃后租约到期可恢复。

更大规模也可替换为 Kafka、RabbitMQ 或云队列，但端口和业务语义保持不变。

## 16. MySQL 为什么能承担队列

**回答：**

当前任务量和一致性需求下，MySQL 能通过 `FOR UPDATE SKIP LOCKED` 提供简单可靠领取，并避免引入第二个消息基础设施。它适合中等吞吐。若预测任务达到高吞吐、多优先级、延迟消息和跨服务消费需求，再迁移专用队列。

## 17. 如何处理 Worker 执行到一半崩溃

**回答：**

任务有 `leased_until`。Worker 崩溃后没有完成任务，租约过期可被另一 Worker 领取。预测结果写入与 Job completed 在同一事务中。因为模型推理本身无业务写副作用，重复推理只增加成本，不会重复修改人工标签。

## 18. 如何处理 RAG 或 LLM 故障

**回答：**

RAG 异常时写 warning 并使用规则、历史模型和 LLM；LLM 异常时使用规则、历史模型和 RAG。历史模型工件在生产缺失则启动失败，不能用 bootstrap 规则静默冒充已训练模型。降级次数进入 Prometheus，人工页面也能看到警告。

## 19. 为什么历史模型故障不直接降级 bootstrap

**回答：**

生产配置承诺使用百万人工数据模型。如果工件丢失却静默换成规则，结果质量会发生巨大变化而健康检查仍显示正常。更安全的策略是启动失败或 Worker 停止消费，明确触发告警。

## 20. 如何衡量项目是否真正提升效率

**回答：**

除了模型 F1，还要看：

- exact match：整道题能否直接提交
- human change rate：多少题需要增删标签
- 每题平均操作时间
- 人工新增/移除标签数
- 高风险标签漏报率
- 预测 P95 延迟
- 降级率和失败率

最终目标是减少人工时间且不牺牲标签质量。

## 21. 如何发布新模型

**回答：**

训练产生不可变工件和 manifest，先过固定离线门禁，再在 staging 回放，随后按操作员或题目哈希灰度。预测快照保存 model_version，人工修改率按版本比较。退化时只需将模型路径或别名切回上一版本，不修改历史预测记录。

## 22. 如何发布新 RAG 索引

**回答：**

新 Embedding 模型或数据快照构建新 Qdrant collection，验证 Point 数、维度、Recall@K 和引用后，通过 alias 或配置切换。保留上一集合快速回滚。不能在在线集合上直接 `--recreate`。

## 23. 网上题目怎么合规使用

**回答：**

公开可访问不等于允许训练。只接入许可证明确或已授权数据，保存 `source_uri` 和 `license_name`，清理个人信息，做内容去重和答案复核。未知许可证网页不进入训练和 RAG。本仓库使用原创合成题验证代码路径。

## 24. 如何防止 Prompt Injection

**回答：**

题干、解析和外部文档都当作数据，不当作系统指令。System Prompt 固定工具和标签边界；模型没有数据库写权限；标签由代码白名单过滤；身份与角色从 JWT Runtime 注入；外部检索只读；高风险结果人工终审。

## 25. JWT 为什么只允许 RS256

**回答：**

API 只持有公钥，身份提供方持有私钥，职责更清晰。代码固定算法并验证 issuer、audience、exp、sub，防止算法混淆和跨系统 Token 被误用。生产不允许调试 Header。

## 26. 如何设计可观测性

**回答：**

分三层：

1. HTTP：模板路由、状态、P95 延迟、request ID。
2. 模型链：预测成功/失败、完整延迟、RAG/LLM 降级。
3. 业务：人工完成量、added/removed 标签和 change rate。

审计表另行保存 actor、action 和 resource。Prometheus label 不使用题目 ID 和用户 ID，避免高基数。

## 27. Vue 前端为什么使用 Composable

**回答：**

`App.vue` 负责布局，`useLabelingWorkbench` 管理任务、标签选择、加载、刷新、提交和错误。这样状态转换可集中理解，页面模板不直接操作 Fetch。当前只有单页，无需引入 Pinia；有跨页面共享状态后再增加全局 Store。

## 28. 前端如何避免快速切学科造成旧请求覆盖

**回答：**

每次 `loadNext` 先中止上一个 `AbortController`，新请求使用新 signal。旧请求即使网络较慢也不会在新学科任务之后写回状态。组件卸载时同样取消请求。

## 29. 为什么生产前端不把 JWT 放 localStorage

**回答：**

localStorage 可被成功执行的 XSS 读取并长期盗用。项目 API 客户端只在内存保存 access token，也支持同域 BFF 的 HttpOnly/SameSite Cookie。具体方案由企业 SSO 决定。

## 30. 这个项目下一步怎么演进

**回答：**

优先顺序是：

1. 接入真实标签规范和匿名化历史数据。
2. 按题目族重新建立无泄漏评测集。
3. 校准每标签阈值并加入高风险召回门禁。
4. 将同步 RAG 两路改为受控并行并增加 cross-encoder rerank。
5. 增加 Worker heartbeat、死信队列和后台任务管理页。
6. 用真实错误分析决定是否训练 Transformer 或 LoRA 模型。
7. 接入企业 OIDC、Kubernetes、OpenTelemetry 和模型网关。

## 31. 一分钟项目总结

> 我实现了一个中小学填空题智能补录系统。后端使用 FastAPI 和 MySQL 管理题目、任务租约、预测快照与人工反馈；用 100 万历史人工标签训练流式多标签模型，用 MySQL ngram 与 Qdrant 做 Hybrid RAG，再通过 LangChain 结构化 LLM 判断，LangGraph 显式编排规则、检索、模型和融合节点。Vue 页面默认勾选模型建议，同时展示来源分数和相似题，人工提交通过幂等键和乐观锁保证一致性。反馈会计算误报漏报、micro/macro F1、完全匹配率和人工修改率，并通过门禁发布新模型。系统还覆盖 JWT、审计、Prometheus、Worker 租约、数据库迁移和模型/RAG 回滚。
