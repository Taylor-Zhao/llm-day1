# Day42 简历条目整理（RAG / Agent / 评测 / 成本优化）

## 使用方法

1. 先按“后端/算法/全栈”选择一个主版本。
2. 再从“可量化结果”中挑 2-3 条放进项目经历。
3. 最后按 JD 关键词微调动词和名词，不要机械照搬。

## 版本 A（偏后端工程）

1. 独立搭建 LLM 后端工程化项目，完成数据构造、LoRA 微调、固定评测、推理优化与服务化上线链路。
2. 基于 FastAPI 设计统一推理服务，落地 API Key 鉴权、滑动窗口限流、统一错误码、指数退避重试与监控接口。
3. 通过统一推理抽象复用基础模型与 LoRA adapter，降低 benchmark、推理 API、服务层三处代码重复率。
4. 建立请求级可观测性：记录 request_id、延迟、token 用量与失败原因，支撑问题定位和容量评估。

## 版本 B（偏算法与效果验证）

1. 设计并执行 LoRA/QLoRA 轻量微调实验，完成从训练数据构造到 adapter 导出的完整闭环。
2. 构建固定评测集对比机制，使用结构分与关键词命中率组成质量指标，验证微调前后效果差异。
3. 对比 fp32、批处理、并发、动态量化等推理策略，形成效果与性能的双维度评估报告。
4. 沉淀实验报告与可复现脚本，保证不同阶段结果可追踪、可复盘、可展示。

## 版本 C（偏全栈与交付）

1. 完成从离线实验到在线服务的端到端交付：训练、评测、推理、API、部署、演示与文档。
2. 提供可公网访问方案（tunnel / Docker / 云主机），并设计健康检查与监控接口保证演示稳定性。
3. 输出 3-5 分钟项目演示脚本与技术决策文档，面向面试场景快速说明技术价值与工程取舍。

## 可量化结果模板（按真实数据替换）

1. 推理接口 P95 延迟从 `<X ms>` 降至 `<Y ms>`，下降 `<Z%>`。
2. 固定评测集上 `tuned_avg_quality` 相比基线提升 `<Δ>`。
3. 服务稳定性：`<N>` 次调用中成功率 `<S%>`，限流与重试策略覆盖主要异常路径。
4. 单次请求平均 token 成本下降 `<C%>`（或吞吐提升 `<T%>`）。

## 一行版项目描述（可放简历项目标题下）

构建并交付一个面向后端场景的 LLM 工程化系统，覆盖 RAG/Agent 能力扩展、微调评测闭环与可上线服务治理（鉴权、限流、重试、监控）。
