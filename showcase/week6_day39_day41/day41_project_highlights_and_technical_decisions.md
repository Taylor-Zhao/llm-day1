# Day41 项目亮点与技术决策文档

## 一句话介绍

这是一个围绕 LLM 后端工程化展开的完整项目：前半段完成 LoRA 微调、固定评测和推理优化，后半段把能力封装成具备鉴权、限流、重试、日志和监控的统一服务。

## 项目亮点

### 1. 不是只做调用，而是做完整闭环

项目覆盖了：

1. 数据构造
2. SFT 微调
3. 固定评测集对比
4. 推理性能优化
5. 统一推理封装
6. 服务化治理

这比单纯“调用一个大模型 API”更能体现工程能力。

### 2. 先验证效果，再服务化

项目顺序不是直接起接口，而是先通过 Day31-Day35 验证：

1. 微调流程能跑通。
2. 固定评测集上有可见提升。
3. 推理模式之间有可对比的速度差异。

这让 Day36-Day38 的服务层不是空壳，而是建立在已经验证过的模型能力之上。

### 3. 统一推理抽象减少重复实现

通过 `UnifiedInferenceEngine`，把：

1. 基础模型加载
2. LoRA adapter 挂载
3. 推理模式切换
4. batch 生成

统一封装到同一个类里。这样 Day33 做 benchmark、Day34 做 API 演示、Day36-Day38 做服务层时，都能复用同一套底层能力。

### 4. 服务层具备最小上线治理能力

Day36-Day38 统一服务已经具备：

1. API Key 鉴权
2. 滑动窗口限流
3. 统一错误码
4. 指数退避重试
5. 请求/延迟/token/失败原因监控

这使项目从“实验脚本”迈向“可上线服务”。

## 技术决策与原因

### 决策 1：微调方案选择 LoRA / QLoRA，而不是全参数训练

原因：

1. 本地资源有限。
2. 目标是快速验证后端问答场景能力增强。
3. LoRA/QLoRA 的工程投入更小，适合个人项目和作品集展示。

### 决策 2：评测采用固定评测集，而不是只看主观印象

原因：

1. 只有固定题目才能公平比较微调前后差异。
2. 便于持续复现和迭代。
3. 更适合在面试中说明“我是如何验证效果的”。

### 决策 3：评分规则先采用启发式质量分

原因：

1. 当前阶段重点是快速建立自动化对比能力。
2. `section_score + keyword_hit_ratio` 足够支撑早期实验判断。
3. 成本低、实现快，适合作为第一版评测器。

局限：

1. 不能完全等价于人工评测。
2. 对复杂语义质量的刻画仍然有限。

### 决策 4：先做统一推理封装，再做服务化

原因：

1. 如果没有统一推理层，服务层会混入大量模型细节。
2. `UnifiedInferenceEngine` 可以把底层复杂度从 API 层剥离出去。
3. 这样服务层更容易专注于鉴权、限流、日志和监控。

### 决策 5：限流采用内存版滑动窗口，而不是 Redis

原因：

1. 当前目标是快速交付最小可运行版本。
2. 单机本地演示足够用。
3. 便于面试时清楚解释原理与后续演进方向。

后续演进：

1. 多实例部署时可切换到 Redis 限流。
2. 指标可接 Prometheus / Grafana。
3. 日志可接 ELK 或云监控平台。

## 简历表达建议

可以写成：

1. 独立完成一个 LLM 后端工程化项目，覆盖数据构造、LoRA 微调、固定评测、推理优化与服务化上线。
2. 设计并实现统一推理引擎，支持基础模型、LoRA adapter、不同推理模式的统一调用。
3. 基于 FastAPI 构建统一服务层，补齐 API Key 鉴权、滑动窗口限流、统一错误码、指数退避重试、请求与 token 级监控。
4. 通过固定评测集验证微调收益，并结合推理延迟与吞吐指标完成效果/性能双维度分析。

## 面试可重点展开的问题

1. 为什么选择 LoRA / QLoRA？
2. 为什么固定评测集比主观对比更重要？
3. `quality` 评分规则为什么这样设计？
4. `fp32` 和 `dynamic_int8` 的差异是什么？
5. 为什么服务层要做统一错误码和 request_id？
6. 如果真上线，限流和监控会如何继续升级？
