# Day40 项目演示视频脚本（3-5 分钟）

## 演示目标

用 3-5 分钟讲清楚三件事：

1. 这个项目解决什么问题。
2. 技术上做了哪些关键工程化能力。
3. 现在已经能跑到什么程度。

## 建议录制结构

### 1. 开场（20-30 秒）

可直接说：

“这是我做的一个 LLM 后端工程化项目。前半部分我完成了从 LoRA/QLoRA、数据构造、SFT 训练、固定评测到推理优化的完整闭环；后半部分我把能力封装成了一个可服务化的 FastAPI 接口，并补上了鉴权、限流、重试、日志和监控，向真实上线形态推进了一步。”

### 2. 展示项目结构（30-40 秒）

建议展示：

1. `run_day31_sft_lora_light.py`：训练闭环。
2. `run_day32_sft_before_after_eval.py`：固定评测对比。
3. `run_day34_unified_inference_api.py`：统一推理封装。
4. `run_day36_day38_unified_service.py`：统一服务层。
5. README 中的流程图和时序图。

可直接说：

“我把训练、评测、推理、服务化分成了不同阶段，每个阶段都有对应脚本、实验报告和 README 文档，便于复盘和对外展示。”

### 3. 展示服务启动（30-40 秒）

操作：

```bash
python run_day36_day38_unified_service.py
```

重点强调：

1. 服务启动时会加载模型和 adapter。
2. 暴露了 `/healthz`、`/v1/inference`、`/metrics` 三个关键接口。

讲解词示例：

“这一步代表项目已经不只是离线脚本，而是具备了对外服务的能力。”

### 4. 展示健康检查与接口调用（60-90 秒）

先调健康检查：

```bash
curl -s http://127.0.0.1:8070/healthz
```

再调主接口：

```bash
curl -s -X POST "http://127.0.0.1:8070/v1/inference" \
  -H "Content-Type: application/json" \
  -H "x-api-key: dev-api-key" \
  -d '{
    "instruction": "请给出订单服务接口超时的排查步骤",
    "user_input": "环境：生产，偶发超时",
    "max_new_tokens": 180,
    "temperature": 0.0,
    "top_p": 1.0
  }'
```

建议强调：

1. 有鉴权。
2. 返回里带 `request_id`、`latency_ms`、`usage`。
3. 说明接口已经具备最小工程化能力。

### 5. 展示监控与治理能力（40-60 秒）

操作：

```bash
curl -s http://127.0.0.1:8070/metrics
```

讲解重点：

1. 能看到总请求数、成功率、平均延迟。
2. 能看到 token 用量。
3. 能统计失败原因。
4. 如果需要，还可以演示不带 `x-api-key` 的 401 或频繁请求触发 429。

### 6. 展示训练与评测闭环（40-60 秒）

建议展示：

1. Day31 训练报告。
2. Day32 前后对比报告。
3. README 中 Day31-Day32 指标对照表。

讲解词示例：

“我没有停留在把服务跑起来，而是先完成了微调闭环，并通过固定评测集确认微调确实带来了结构和关键词覆盖上的提升，然后再把能力服务化。”

### 7. 收尾（20-30 秒）

可直接说：

“这个项目对我来说最大的价值，不是单点模型调用，而是把训练、评测、推理优化和服务化治理串成了一个完整工程闭环。后续我会继续推进公网部署、演示完善和简历化表达。”

## 录制建议

1. 全程控制在 3-5 分钟，不要展开讲所有实现细节。
2. 优先展示“能跑的东西”和“有数据支撑的结论”。
3. README 中的图和报告可以作为讲解辅助，不要只读代码。
4. 先提前跑热一次服务，避免录屏时首次加载模型过慢。
