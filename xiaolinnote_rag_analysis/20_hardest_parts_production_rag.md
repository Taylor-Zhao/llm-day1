# 20. RAG 落地最难什么：预处理、检索调优与评估

- 原文：[实际落地中 RAG 最难的地方](https://xiaolinnote.com/ai/rag/20_hardest_parts.html)
- 主题定位：从 Demo 走向生产的系统性难点总结。
- 一句话结论：RAG 难点不是调用 Embedding API，而是让脏数据变成可靠证据、让检索可诊断、让每次改动可量化且可回滚。

## 1. 三大难点

```mermaid
flowchart LR
    A[复杂原始文档] --> P[解析 清洗 结构保留]
    P --> R[切块 Embedding 混合检索]
    R --> G[门控 生成 引用]
    G --> E[离线与线上评估]
    E --> F[失败样本与知识缺口]
    F --> P
    F --> R
```

### 文档预处理

PDF 文本流可能打乱双栏顺序，表格会丢失表头关系，扫描件需要 OCR，图片和公式需要多模态解析，代码需要 AST/语法边界。垃圾输入无法靠更强 Embedding 修复。

生产解析管线应保留文档层级、页码、表格单元格、图片说明、权限、版本和解析器置信度，并对空文档、乱码、重复页做质量门禁。

### 检索质量调优

失败可能来自解析、Chunking、Embedding、Query、Sparse 词典、融合、Rerank 或过滤。必须有分阶段 trace：每路候选、分数、排名、最终 Prompt 和引用。

### 效果评估

自然语言答案不唯一，单一端到端分数无法定位故障。应拆成检索、上下文、生成、线上业务四层，并维护代表真实流量的回归集。

## 3. 当前最明显缺口

1. 没有 PDF、Word、HTML、表格、OCR、图片和代码结构解析层。
2. 没有生产向量库、metadata 权限预过滤和并发写入。
3. 没有真实 Cross-encoder、多模型 Embedding A/B 和 RAGAs。
4. 没有动态持久化索引、消息队列、蓝绿服务切换。
5. 没有完整服务的认证、限流、观测、隐私和 Prompt Injection 防御。

[rag_capabilities_reference.py](examples/rag_capabilities_reference.py) 补齐部分算法与控制骨架，但没有解决解析、基础设施和生产治理问题。

## 4. 生产化路线图

1. **数据合同**：先定义支持格式、metadata、权限和更新 SLA。
2. **黄金集**：从真实问题标注正确证据和不可回答样本。
3. **可解释基线**：Flat Dense + 固定切块 + 引用，建立指标。
4. **逐层优化**：按失败类型增加 Parent-Child、BM25、RRF、Rerank、Rewrite。
5. **可信治理**：质量门控、结构化引用、Prompt Injection 隔离、人工升级。
6. **发布运维**：缓存、trace、成本、蓝绿索引和回滚演练。

每一步都应有退出标准，而不是“功能做完”。例如新增 Rerank 的验收可要求 MRR 提升、P95 增幅受控、负样本误答不退化。

## 5. 常见误区

- Demo 能答几题不等于可上线。
- 只调 Prompt 无法修复错误解析和漏召。
- 只看平均质量会掩盖权限、时效和长尾问题。
- 所有文档用同一解析器/切块器会破坏结构。
- 没有版本和回滚的知识更新会让错误立即污染线上。

## 6. 模拟面试

**Q1：为什么文档预处理往往比核心 RAG 代码更难？**  
A：真实格式复杂且结构承载语义，解析错误会不可逆地污染后续索引和引用。

**Q2：如何系统排查检索差？**  
A：从原文解析、chunk、各路候选、融合排名、Rerank 到最终 Prompt 逐层 trace，并用 Hit@K/MRR 定位。

**Q3：为什么评估是生产难点？**  
A：答案无唯一文本、故障跨多层、标注昂贵且用户分布持续变化。

**Q4：当前项目最值得保留的方法是什么？**  
A：逐日建立基线、单变量实验、离线评估、延迟成本分析和发布门禁的闭环。

**Q5：下一步生产化优先做什么？**  
A：先做数据合同与解析质量、真实黄金集和可观测 trace，再选择昂贵高级范式。
